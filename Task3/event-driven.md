# Переход на Event-Driven архитектуру

### 1. Проблемы

Текущая реализация имеет очевидные проблемы: при получении информации из сервиса ins-product-aggregator, этот сервис делает синхронные запросы к внешним провайдерам и возвращает ответ. При том сервисы хранят локально информацию, полученную из этого сервиса.

Т.к. все происходит в рамках одного синхронного запроса, есть проблема в высокой латентностью запроса, а также наличием ошибок от провайдеров. Это приводит к ошибкам или долгим запросам на стороне вызывающих сервисов.
Увеличение количества провайдеров также может усугубить проблему.

Также отсутствует кеширование на стороне сервиса ins-product-aggregator, из-за чего сервис каждый раз отправляет запросы к провайдерам. Причина, в целом, понятна: необходимо получить актуальную информацию от провайдеров. Однако, если развернуто несколько реплик сервисов core-app и ins-comp-settlement и отсутствует централизованный кеш, то в определенный промежуток времени будет отправляться несколько запросов к ins-product-aggregator, который в свою очередь будет отправлять запросы к провайдерам. Провайдеры в этом случае могут ограничивать количество запросов, в следствие чего будем получать ошибки.

Если нет фолбека в сервисе core-app на использование данных из реплики, то при ошибочном запросе к ins-product-aggregator может проихойти отказ в обслуживании.

Также есть дублирование логики хранения информации. Если под "репликой" имеется в виду локальный кеш, то имеет смысл установить сделать его общим для нескольких сервисов, и брать информацию оттуда для необходимых сервисов. Иначе может происхойти рассинхронизация данных между сервисами, что может привести к неизвестным результатам.

Также у сервиса ins-comp-settlement есть зависимость от core-app, и в случае недоступности, это приведет к невозможности расчета страховок. При этом не указано использование ретраев.

### 2. Предложения

1. Для получения информации об оформленных страховках можно использовать следующую стратегию:
Использовать outbox таблицу в сервисе core-app, в которую будут записываться все оформленные страховки. В этом случае можно оставить связь через rest, но поставить демона\таску, которая будет вычитывать все новые записи из этой таблицы и отправлять их в ins-comp-settlement. В этом случае можно указать более коротки промежуток времени: например, 30 или 60 минут для отправки данных и помечать их как выполненные после обработки в сервисы ins-comp-settlement. При необходимости также можно отправлять и в другие сервисы. При этом необходимо в потребителях доработать систему, чтобы она поддерживала идемпотентность, для исключения дублирования данных.
Аналогичным образом можно сделать и при взаимодействии core-app с сервисом client-info. Однако, учитывая что в данный момент нет проблем с взаимодействие, этот пункт на данном этапе опустим.

2. Для получения информации по продуктам можно использовать автоматический опрос провайдеров в определенный промежуток времени(например, каждые 15 минут) и дальше придерживаться одной из 2 стратегий:
2.1. Отправлять данные через Кафку, от которой смогут получать данные все необходимые сервисы.
2.2. Хранить данные в кеше и сервисам-потребителям запрашивать данные из кеша.

Т.к. объем данных и количество запросов по продуктам не высоко, то в качестве быстрой реализации имеет смысл использовать централизованное хранилище временных данных в Redis. 

Однако централизованный кеш а данном случае может быть spof. В этом случае в качестве долговременного решения стоит использовать кафку для передачи информации по продуктам в сервисы-потребители.

3. Т.к. сервис ins-product-aggregator имеет интеграции с внешними провайдерами, имеет смысл использовать его для передачи данных по оформленным страховкам, чтобы не дублировать логику в сервисе ins-comp-settlement. Для этого можно отправлять эти данные в сервис ins-product-aggregator, который будет по текущему апи передавать данные к внешним провайдерам. В этом случае сервис ins-product-aggregator может быть преобзразован в гейтвей для общения с внешними провайдерами с доп функционалом отправки данных в кафку.
